# Демо: автоматизированный контур «заказ → оплата → выдача доступа»

Учебная модель ключевого процесса ООО «Сервис», описанного в курсовой работе
(глава 3 и 4). Написана на Python 3.9+ **только со стандартной библиотекой**:
`http.server`, `sqlite3`, `hmac`, `hashlib`, `secrets`, `unittest`.
Внешних зависимостей нет, устанавливать ничего не нужно.

## Что показывает демо

| Свойство целевого процесса | Где в коде |
|---|---|
| Заказ создаётся клиентом без участия оператора | `SubscriptionService.create_order` |
| Уведомление агрегатора принимается только с верной HMAC-подписью | `verify_signature`, `handle_webhook` |
| Повтор уведомления не даёт второго начисления (идемпотентность по внешнему id платежа) | таблица `payments`, первичный ключ `external_id` |
| Сумма платежа сверяется с суммой заказа | `_apply_payment` → `amount_mismatch` |
| Подписка активируется или продлевается сразу после оплаты | `_activate` |
| Токен доступа выдаётся клиенту один раз, в базе хранится только хеш | таблицы `deliveries`, `subscriptions` |
| Зависшие заказы сверяются по расписанию: найденная оплата проводится, остальные отменяются | `reconcile_stale_orders`, фоновый поток в `app.py` |
| Каждое действие пишется в журнал (кто, что, когда) без секретов | таблица `audit_log` |
| Служебные эндпоинты закрыты отдельным токеном администратора | `/admin/*`, `X-Admin-Token` |

## Запуск

Из корня репозитория:

```bash
export DEMO_WEBHOOK_SECRET=change-me        # заглушка; в эксплуатации — из хранилища секретов
export DEMO_ADMIN_TOKEN=change-me-too       # необязательно, без него /admin/* закрыт
python3 -m demo.app
```

Без `DEMO_WEBHOOK_SECRET` сервис не запускается (код возврата 2) — это сделано
намеренно: «секрет по умолчанию» в коде — типичная причина утечек.

Необязательные переменные: `DEMO_PORT` (8000), `DEMO_DB_PATH` (`demo-service.db`),
`DEMO_PENDING_TTL` (срок жизни неоплаченного заказа, 1800 с),
`DEMO_RECONCILE_INTERVAL` (период сверки, 60 с), `DEMO_ACCESS_LOG=1` (журнал запросов).

### Пример сеанса

```bash
# 1. Клиент создаёт заказ
curl -s -X POST localhost:8000/orders -d '{"email":"client@example.org","plan":"1m"}'
# → {"order_id": "ord_…", "amount": 29900, "plan": "1m", "order_key": "…"}

# 2. Агрегатор присылает уведомление (здесь подпись считаем сами)
BODY='{"order_id":"ord_…","external_id":"pay-1","amount":29900,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$DEMO_WEBHOOK_SECRET" | awk '{print $NF}')
curl -s -X POST localhost:8000/webhooks/payment -H "X-Signature: $SIG" -d "$BODY"
# → {"result": "processed", …}; повтор той же команды → {"result": "duplicate", …}

# 3. Клиент забирает токен доступа (ровно один раз)
curl -s localhost:8000/orders/ord_… -H "X-Order-Key: <order_key из шага 1>"

# 4. Журнал действий
curl -s localhost:8000/admin/audit -H "X-Admin-Token: $DEMO_ADMIN_TOKEN"
```

## Тесты

```bash
python3 -I -m unittest discover -s demo/tests -t .
```

30 тестов: модульные (`test_service.py`, с подменой часов) и сквозные
(`test_http.py`, настоящий HTTP-сервер на свободном порту). Среди проверок:
неверная подпись → 403; подделанное тело → отказ; повтор уведомления → одно
начисление; неверная сумма → 422 без активации; просроченный заказ → отменён
сверкой; потерянное уведомление → оплата найдена сверкой, а запоздавший webhook
не начисляет повторно; оплата после отмены → доступ всё равно выдаётся; токен
выдаётся один раз и не попадает в журнал.

## Ограничения (сознательные)

Демо — модель, а не продукт: одна база SQLite и один процесс, нет TLS,
ограничения частоты запросов, ротации ключей, отправки писем и реального API
агрегатора (его заменяет функция `status_checker`, передаваемая в сверку).
Как эти вопросы решаются в целевой архитектуре — см. `docs/04-arhitektura.md`.
