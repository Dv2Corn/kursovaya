# Демо: «объект → модерация → закрытый каталог → подписчик → показ»

Учебная модель ключевых процессов ООО «Квартирант плюс», описанных в
курсовой работе (главы 2 и 3). Написана на Python 3.9+ **только со
стандартной библиотекой**: `http.server`, `sqlite3`, `hmac`, `hashlib`,
`secrets`, `unittest`. Внешних зависимостей нет, устанавливать ничего не нужно.

## Что показывает демо

| Свойство целевого процесса | Где в коде |
|---|---|
| Агент заносит эксклюзив через форму, объект ждёт модерации | `AgencyService.submit_listing`, `moderation_queue` |
| Модератор публикует или отклоняет объект (с причиной) | `approve_listing`, `reject_listing` |
| Закрытый каталог виден только клиентам с действующей подпиской | `catalog`, `listing_detail`, `_is_active` |
| Заказ подписки создаётся клиентом без участия сотрудника | `create_order` |
| Уведомление агрегатора принимается только с верной HMAC-подписью | `verify_signature`, `handle_gateway_webhook` |
| Вторая схема оплаты — внутренняя валюта мессенджера | `handle_messenger_payment` |
| Повтор уведомления не даёт второго начисления | таблица `payments`, первичный ключ `(provider, external_id)` |
| Сумма платежа сверяется с ценой тарифа | `_apply_payment` → `amount_mismatch` |
| Подписка активируется сразу после оплаты, продление — «от конца срока» | `_activate` |
| Зависшие заказы сверяются: найденная оплата проводится, остальные отменяются | `reconcile_stale_orders` |
| Новый объект подбирается под сохранённые запросы подписчиков (район, цена, комнаты) | `save_search`, `approve_listing` |
| Очередь уведомлений без дублей, неудачная отправка повторяется | таблица `notifications` (`UNIQUE`), `dispatch_notifications` |
| Запись на показ: слот, подтверждение агентом, напоминание за сутки | `request_viewing`, `confirm_viewing`, `send_viewing_reminders` |
| Подписка заканчивается по сроку, за 3 дня приходит предупреждение | `run_subscription_lifecycle` |
| Журнал действий (кто, что, когда) без секретов и почты клиентов | таблица `audit_log`, `_audit` |
| Руководитель видит воронку «просмотр → показ → сделка» и вклад агентов | `metrics` |
| Роли администрирования: владелец и модератор | `/admin/*`, `X-Admin-Token` |

## Запуск

Из корня репозитория:

```bash
export DEMO_WEBHOOK_SECRET=change-me          # заглушка; в эксплуатации — из хранилища секретов
export DEMO_ADMIN_TOKEN=change-me-owner       # роль «владелец»; без него /admin/* закрыт
export DEMO_MODERATOR_TOKEN=change-me-mod     # роль «модератор» (необязательно)
export DEMO_MESSENGER_SECRET=change-me-msg    # оплата валютой мессенджера (необязательно)
python3 -m demo.app
curl -s localhost:8000/health
```

Без `DEMO_WEBHOOK_SECRET` сервис не запускается (код возврата 2): «секрет по
умолчанию» в коде — типичная причина утечек.

Необязательные переменные: `DEMO_PORT` (8000), `DEMO_DB_PATH`
(`demo-agency.db`), `DEMO_PENDING_TTL` (срок жизни неоплаченного заказа,
1800 с), `DEMO_JOBS_INTERVAL` (период планировщика, 60 с), `DEMO_ACCESS_LOG=1`
(журнал запросов).

### Пример сеанса

```bash
OWNER="X-Admin-Token: $DEMO_ADMIN_TOKEN"

# 1. Владелец заводит агента (токен агента показывается один раз)
curl -s -X POST localhost:8000/admin/agents -H "$OWNER" -d '{"name":"Ирина"}'
# → {"agent_id": "ag_…", "agent_token": "…"}

# 2. Агент заносит эксклюзив, модератор публикует
curl -s -X POST localhost:8000/listings -H "X-Agent-Token: <agent_token>" \
  -d '{"title":"2-комнатная у парка","district":"Центральный","price":7500000,"rooms":2,"area":54.5}'
curl -s -X POST localhost:8000/admin/listings/obj_…/approve -H "$OWNER"

# 3. Клиент заказывает подписку и сохраняет запрос
curl -s -X POST localhost:8000/orders -d '{"email":"client@example.org","plan":"1m"}'
# → {"order_id": "ord_…", "amount": 99000, "units": 990, "client_key": "…"}
curl -s -X POST localhost:8000/searches -H "X-Client-Key: <client_key>" \
  -d '{"district":"Центральный","price_max":8000000,"rooms_min":2}'

# 4. Агрегатор присылает уведомление (здесь подпись считаем сами)
BODY='{"order_id":"ord_…","external_id":"pay-1","amount":99000,"status":"succeeded"}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$DEMO_WEBHOOK_SECRET" | awk '{print $NF}')
curl -s -X POST localhost:8000/webhooks/payment -H "X-Signature: $SIG" -d "$BODY"
# → {"result": "processed", …}; повтор той же команды → {"result": "duplicate", …}

# 5. Подписчик открывает закрытый каталог и записывается на показ
curl -s localhost:8000/catalog -H "X-Client-Key: <client_key>"
curl -s -X POST localhost:8000/viewings -H "X-Client-Key: <client_key>" \
  -d "{\"listing_id\":\"obj_…\",\"slot_at\":$(( $(date +%s) + 172800 ))}"

# 6. Руководитель: показатели и журнал
curl -s localhost:8000/admin/metrics -H "$OWNER"
curl -s localhost:8000/admin/audit -H "$OWNER"
```

Уведомления о новом объекте ставятся в очередь в момент публикации (если
у подписчика уже был сохранён запрос) и отправляются планировщиком; в демо
«отправка» только отмечает их доставленными, посмотреть очередь можно через
`GET /notifications`.

## Тесты

```bash
python3 -I -m unittest discover -s demo/tests -t .
```

60 тестов, около 6 секунд: модульные (`test_service.py`, с подменой часов) и
сквозные (`test_http.py`, настоящий HTTP-сервер на свободном порту). Среди
проверок: каталог закрыт без подписки и закрывается ровно в момент окончания
срока, даже если плановое задание ещё не выполнялось; неверная подпись → 403;
подделанное тело → отказ; повтор уведомления → одно начисление; неверная
сумма → 422 без активации; потерянное уведомление находится сверкой, а
запоздавший webhook не начисляет повторно; оплата после отмены всё равно
активирует подписку; уведомление получают только подписчики с подходящим
запросом и только один раз; занятый слот показа → 409; чужой агент не может
подтвердить показ; модератор не видит журнал; в журнале нет ключей, токенов и
адресов почты.

## Ограничения (сознательные)

Демо — модель, а не продукт: одна база SQLite и один процесс, нет TLS,
ограничения частоты запросов, ротации ключей, настоящей отправки сообщений,
загрузки фотографий и документов, промокодов, подарочных подписок и
реферальной программы; реальный API агрегатора заменяет функция
`status_checker`, передаваемая в сверку. Как эти вопросы решаются в целевой
архитектуре — см. `docs/04-arhitektura.md`.
